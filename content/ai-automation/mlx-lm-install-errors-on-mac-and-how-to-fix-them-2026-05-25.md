# `mlx-lm` 설치했는데 왜 안 될까? Apple Silicon Mac에서 자주 막히는 에러와 해결 가이드

로컬 AI 입문에서 제일 먼저 깨지는 환상은 이런 거다. `pip install mlx-lm` 한 줄이면 다 끝날 줄 알았는데, 막상 해보면 설치는 됐는지 애매하고, 모델은 안 받아지고, 명령어는 대기 상태처럼 멈춰 있고, 어떤 모델은 또 `trust_remote_code` 같은 낯선 경고를 꺼낸다.

이 지점에서 많은 사람이 헷갈린다. “내 맥이 문제인가?”, “명령어가 틀렸나?”, “이 모델은 원래 안 되는 건가?”

그래서 이번 글은 `mlx-lm` 자체 소개보다 한 단계 더 현실적으로 간다. **Apple Silicon Mac에서 실제로 자주 막히는 지점**을 기준으로, 어떤 증상일 때 어디부터 보면 되는지를 한 번에 정리했다.

## 먼저 결론

- `mlx-lm` 문제는 의외로 복잡한 버그보다 **환경 조건, 모델 경로, 첫 다운로드, 옵션 누락**에서 많이 시작된다.
- 초보자가 가장 먼저 볼 건 네 가지다. **Apple Silicon인지, `--model` 경로가 맞는지, 첫 실행이라 다운로드 중인 건 아닌지, `--prompt`를 넣었는지**다.
- 어떤 모델은 `--trust-remote-code`가 필요하다.
- 큰 모델이 느리거나 메모리 경고를 낼 때는, 무작정 “고장”으로 보기보다 **모델 크기와 macOS 메모리 동작**부터 봐야 한다.
- `iogpu.wired_limit_mb` 같은 설정은 분명 도움될 수 있지만, **입문자가 처음부터 제일 먼저 손댈 항목은 아니다.**

## 1) 아예 전제가 안 맞는 경우: Intel Mac이거나 환경이 다름

이건 생각보다 자주 놓친다.

`mlx-lm`은 **Apple Silicon 중심** 흐름으로 보는 게 맞다. 즉 M1, M2, M3, M4, M5 계열 Mac에서 생각하는 로컬 AI 실행 경험을 전제로 한다. Intel Mac이나 Windows/Linux 환경에서 같은 글을 그대로 따라 하면, 당연히 체감도 다르고 막히는 지점도 달라진다.

### 이렇게 보이면 먼저 의심
- 같은 명령인데 다른 사람 설명과 전혀 다르게 움직인다.
- 속도나 메모리 동작이 너무 이상하다.
- MLX 기반 설명이 내 환경과 잘 안 맞는다.

### 먼저 할 일
- 내 장비가 Apple Silicon인지 확인한다.
- 이 글이 다루는 전제가 내 환경과 같은지 먼저 맞춘다.

## 2) 명령어는 맞는데 첫 줄부터 안 되는 경우: 모델 경로가 틀림

이건 진짜 흔하다. 특히 블로그, 메신저, 커뮤니티를 거친 모델 이름은 생각보다 자주 틀린다.

예를 들어,
- 저장소 소유자가 다르거나
- `4bit`, `6bit`, `Instruct`, `MLX` 접미사가 하나 빠졌거나
- 존재하지 않는 `mlx-community/...` 경로를 그대로 믿고 복붙한 경우가 많다.

### 증상
- 모델을 못 찾는다.
- 처음부터 저장소 관련 오류가 난다.
- “이 모델 진짜 있는 거 맞아?” 싶은 상황이 나온다.

### 해결
- Hugging Face 저장소 경로를 먼저 다시 확인한다.
- “비슷한 이름” 말고 **정확한 전체 경로**로 넣는다.
- 처음엔 검증된 작은 모델로 동작부터 확인한다.

예:

```bash
mlx_lm.generate \
  --model mlx-community/Llama-3.2-3B-Instruct-4bit \
  --prompt "안녕! 지금 정상적으로 실행되고 있는지 짧게 말해줘."
```

## 3) 멈춘 것처럼 보이는데 사실은 다운로드 중인 경우

초보자 입장에서는 이게 제일 불안하다. 커서만 깜빡이고, 뭔가 엄청 느리고, 아무 일도 안 일어나는 것처럼 보인다.

그런데 실제로는 **처음 모델을 내려받는 중**인 경우가 많다.

큰 모델일수록 이 시간은 길어진다. 그러니 첫 시도에서 바로 “고장”이라고 단정하면 안 된다.

### 증상
- 첫 실행이 유난히 오래 걸린다.
- 응답이 바로 안 나온다.
- 멈춘 것처럼 느껴진다.

### 해결
- 처음 실행인지 먼저 확인한다.
- 작은 모델로 먼저 테스트해본다.
- 네트워크 상태와 저장공간도 같이 본다.

## 4) 명령어가 이상하게 가만히 있는 경우: `--prompt` 없이 시작함

`mlx_lm.generate`를 처음 만지는 사람은 “일단 모델만 넣으면 뭔가 나오겠지”라고 생각하기 쉽다. 그런데 실제로는 **명확한 프롬프트를 같이 주는 편**이 훨씬 덜 헷갈린다.

### 증상
- 아무 반응이 없는 것처럼 느껴진다.
- 내가 기대한 채팅형 응답이 바로 안 보인다.

### 해결
가장 안전한 첫 테스트는 늘 이쪽이다.

```bash
mlx_lm.generate \
  --model mlx-community/Llama-3.2-3B-Instruct-4bit \
  --prompt "안녕! 로컬 AI 테스트 중이야. 한 줄로 인사해줘."
```

대화형으로 쓰고 싶다면 차라리 `mlx_lm.chat`으로 넘어가는 편이 더 직관적일 수 있다.

## 5) Qwen 계열 등에서 갑자기 `trust_remote_code` 이야기가 나오는 경우

이건 초보자가 가장 당황하는 메시지 중 하나다. 이름부터 무섭다. 하지만 뜻은 비교적 단순하다.

어떤 모델은 Hugging Face 쪽의 **사용자 정의 토크나이저나 코드**를 신뢰해야 제대로 로드된다. 공식 `mlx-lm` README에서도 이런 경우 `--trust-remote-code`를 쓸 수 있다고 안내한다.

### 증상
- 특정 모델에서만 로딩이 안 된다.
- Qwen 계열이나 비교적 새로운 구조에서 관련 경고가 뜬다.
- 토크나이저/모델 로드 관련 오류가 난다.

### 해결
모델 출처를 확인한 뒤, 신뢰할 수 있다고 판단되면 이렇게 시도한다.

```bash
mlx_lm.generate \
  --model <모델경로> \
  --trust-remote-code \
  --prompt "짧게 자기소개해줘."
```

다만 여기서 중요한 건 하나다.

> 이 옵션은 편의 버튼이 아니라, 외부 모델 저장소의 커스텀 코드를 신뢰하겠다는 뜻이다.

즉 초보자일수록 **모델 출처 확인**을 먼저 하는 습관이 중요하다.

## 6) 큰 모델이 너무 느리거나 경고를 내는 경우

이건 “고장”보다는 **장비와 모델 크기의 현실**에 더 가깝다.

공식 README에서도 큰 모델이 총 RAM에 비해 너무 크면 느릴 수 있다고 안내하고 있다. 또 `mlx-lm`이 메모리를 더 효율적으로 다루는 최적화는 **macOS 15 이상**을 전제로 하는 부분이 있다.

### 증상
- 분명 실행은 되는데 너무 느리다.
- 경고가 뜬다.
- 작은 모델은 괜찮은데 큰 모델만 힘들다.

### 해결
- 먼저 작은 모델로 비교한다.
- 4bit 같은 더 가벼운 양자화 모델을 고른다.
- 정말 큰 모델을 돌릴 때만 메모리 설정을 검토한다.

여기서 중요한 건, 입문자는 무조건 “더 큰 모델”보다 **내 Mac에서 반복 가능한 모델**을 먼저 찾는 게 낫다는 점이다.

## 7) `iogpu.wired_limit_mb` 이야기가 나올 때

이건 어느 순간부터 로컬 AI 커뮤니티에서 자주 보이는 설정이다. 큰 모델이 느리거나 메모리 한계에 부딪힐 때 도움이 될 수 있다.

공식 README 흐름에도, 큰 모델이 RAM에 비해 커서 느릴 경우 `sudo sysctl iogpu.wired_limit_mb=N` 같은 조정을 검토할 수 있다는 안내가 있다.

하지만 나는 이걸 **초보자의 첫 해결책**으로 권하지는 않는다.

### 왜 조심해야 하냐
- 시스템 메모리 동작과 연결된 영역이다.
- 값만 올린다고 모든 문제가 해결되는 건 아니다.
- 모델 크기, 컨텍스트, KV 캐시 상황을 같이 봐야 한다.

### 내 추천 순서
1. 작은 모델로 먼저 재현해본다.
2. 4bit 모델로 바꿔본다.
3. macOS 버전과 RAM 여유를 확인한다.
4. 그다음에도 큰 모델이 계속 느릴 때만 `wired limit`을 검토한다.

즉 이건 “처음부터 꼭 해야 하는 설정”이 아니라, **조금 더 깊게 들어갈 때 보는 고급 카드**에 가깝다.

## 8) 하이픈이 깨져서 생기는 복붙 오류

이건 별거 아닌 것 같아도 실제론 자주 나온다.

블로그나 메신저를 거치면 `--model` 같은 옵션이 긴 대시로 바뀌어버리는 경우가 있다. 터미널에서는 그게 전혀 다른 문자라서 그대로는 안 먹는다.

### 해결
- 옵션 앞은 반드시 `--` 하이픈 두 개인지 확인한다.
- “겉보기에 비슷한 문자”를 조심한다.

## 9) 무엇부터 확인해야 할지 모르겠을 때 쓰는 최소 점검 순서

헷갈릴 때는 순서를 줄이면 된다. 나는 보통 이렇게 본다.

### 가장 먼저
1. Apple Silicon Mac인가?
2. `mlx-lm` 설치는 됐나?
3. 작은 모델 경로는 맞나?
4. `--prompt`를 넣었나?
5. 첫 실행이라 다운로드 중인 건 아닌가?

### 그다음
6. 특정 모델만 안 되면 `--trust-remote-code` 필요 여부 확인
7. 큰 모델만 느리면 macOS 버전, RAM, 모델 크기 비교
8. 그래도 필요할 때만 `iogpu.wired_limit_mb` 검토

## 바로 써볼 안전한 테스트 명령

### 생성 테스트

```bash
mlx_lm.generate \
  --model mlx-community/Llama-3.2-3B-Instruct-4bit \
  --prompt "안녕! 지금 정상적으로 실행 중이면 한 문장으로 알려줘."
```

### 채팅 테스트

```bash
mlx_lm.chat --model mlx-community/Llama-3.2-3B-Instruct-4bit
```

### Qwen 계열에서 remote code가 필요한 경우 예시

```bash
mlx_lm.generate \
  --model <Qwen-계열-모델경로> \
  --trust-remote-code \
  --prompt "짧게 자기소개해줘."
```

## 남겨둘 판단

`mlx-lm`에서 초보자가 막히는 이유는 대개 거창한 기술 문제보다 훨씬 현실적이다.

- 모델 이름이 틀렸거나
- 처음 다운로드를 기다리지 못했거나
- 프롬프트 없이 실행했거나
- 큰 모델을 너무 빨리 잡았거나
- 특정 모델의 로딩 조건을 놓쳤거나

대부분은 여기서 시작한다.

그래서 로컬 AI 입문에서 제일 중요한 태도는 “왜 안 되지?”라고 당황하는 게 아니라, **작게 확인하고, 조건을 분리하고, 성공한 조합부터 확보하는 것**이다. 그 순서로 가면 생각보다 빨리 풀린다.
