# Oh My Hermes 심층 분석 · 초보 개발자도 이해할 수 있게 풀어본 설치형 AI CTO 팩

AI 에이전트 툴을 처음 보면 보통 이런 기대를 하게 된다.

“말만 하면 알아서 앱 만들고, 배포하고, 운영까지 해주는 거 아냐?”

그런데 현실은 그 사이에 빠진 게 많다. 누가 요구사항을 정리하는지, 누가 어느 도구를 쓸지 결정하는지, 누가 배포하고 헬스체크하고 알려주는지 같은 운영 레이어가 비어 있으면, 에이전트는 금방 인상적인 데모에서 멈춘다.

이번에 읽은 <https://github.com/Salomondiei08/oh-my-hermes> 는 바로 그 빈칸을 메우려는 프로젝트다. 한 줄로 말하면, Hermes Agent 위에 얹는 <strong>설치형 운영 패키지</strong>에 가깝다.

## 먼저 결론

- Oh My Hermes는 새로운 AI 에이전트 런타임이 아니라, <strong>Hermes를 더 실전적으로 쓰기 위한 스킬·워크플로우·에이전트 묶음</strong>이다.
- 초보 개발자 입장에서는 “만능 자동 개발봇”으로 보기보다, <strong>Hermes용 운영 기본 세트</strong>로 이해하는 쪽이 정확하다.
- 이 저장소의 핵심 가치는 코드 생성보다 <strong>요구사항 정리 → 엔진 선택 → 배포 → 헬스체크 → 알림</strong> 같은 흐름을 하나의 습관으로 묶어준다는 데 있다.
- 반대로 Hermes 자체를 아직 안 써봤다면, 이 프로젝트를 먼저 설치하는 것보다 <strong>Hermes가 무엇이고 무엇을 잘하는지</strong>부터 이해하는 게 낫다.
- 문서는 꽤 잘 써놨지만, 초보자에게는 용어가 한 번에 많이 쏟아진다. 그래서 처음에는 전체를 다 보지 말고 <strong>README → installation → architecture → workflows</strong> 순서로 읽는 게 좋다.

## 이 프로젝트를 한 문장으로 설명하면

README의 표현을 한국어로 풀면 대략 이렇다.

> Hermes를 그냥 똑똑한 채팅 도구로 두지 말고, 실제 소프트웨어 프로젝트를 만들고 굴리는 운영자처럼 쓰게 해주는 의견 강한 워크플로우 팩.

여기서 중요한 단어가 두 개다.

### 1) Hermes 자체가 아니라 Hermes 위의 레이어다

이 프로젝트는 스스로 서버가 되거나 별도 데몬으로 도는 프로그램이 아니다. `docs/architecture.md` 에서도 분명히 말한다.

- Oh My Hermes는 런타임이 아니다
- 파일 묶음이다
- Hermes가 이 파일들을 읽고 실행한다

즉, 관계를 쉽게 그리면 이렇다.

- <strong>Hermes</strong> = 실제로 오래 켜져 있는 운영자
- <strong>Oh My Hermes</strong> = Hermes에게 무엇을 어떻게 하라고 가르치는 운영 매뉴얼 묶음

이 차이를 초반에 이해하면 훨씬 덜 헷갈린다.

### 2) “의견 강한(opinionated)” 기본값을 준다

이 프로젝트가 하려는 건 자유도를 늘리는 게 아니라, 처음엔 오히려 줄이는 쪽에 가깝다.

기본값이 꽤 분명하다.

- 배포는 Vercel
- 데이터베이스는 Supabase
- 에러 추적은 Sentry
- 업타임 체크는 Uptime Kuma
- 알림은 Slack webhook
- 코딩 엔진은 Claude Code 또는 Codex

초보자에게는 이게 장점이다. 무엇을 고를지 고민하느라 시작도 못 하는 상황을 줄여주기 때문이다.

## 저장소를 읽으며 가장 먼저 보인 구조

이 저장소를 깊게 읽어보면 사실상 다섯 덩어리로 나뉜다.

1. `skills/`
2. `workflows/`
3. `agents/`
4. `scripts/`
5. `docs/`

### skills: Hermes가 불러 쓰는 작업 카드

가장 중요한 폴더는 `skills/` 다. 여기에는 Hermes가 특정 요청을 받았을 때 불러 쓸 문서형 스킬이 들어 있다.

예를 들면 이런 것들이다.

- `clarify-requirements`
- `product-brief`
- `design-handoff`
- `choose-engine`
- `deploy-to-vercel`
- `connect-supabase`
- `health-check`
- `send-notification`

초보자 기준으로 쉽게 말하면,
이건 “AI에게 어떤 순서로 일하게 할지 적어둔 작업 카드”에 가깝다.

### workflows: 스킬 여러 개를 한 흐름으로 묶은 것

`workflows/`는 더 큰 단위다.

예를 들어 `idea-to-deploy`는 아래 흐름을 묶는다.

- 요구사항 정리
- 제품 브리프 작성
- 디자인 핸드오프
- 엔진 선택
- 구현
- Vercel 배포
- Supabase 연결
- 알림
- 사후 헬스체크

즉, 스킬이 한 동작이라면 워크플로우는 작은 프로젝트 한 판이다.

### agents: 역할 분담된 가상 팀

여기가 이 저장소의 인상적인 부분이다. 에이전트를 한 명으로 보지 않고 역할을 나눈다.

- CTO
- PM
- Dev
- QA
- Ops

초보자가 여기서 바로 감 잡으면 좋은 건, AI를 “한 명의 만능 인물”로 보지 않는다는 점이다. 실제 팀처럼 나누면 오히려 이해가 쉬워진다.

- PM은 이슈를 정리하고
- Dev는 구현하고
- QA는 리뷰하고
- Ops는 배포하고 모니터링한다
- CTO는 전체를 조율한다

이 사고방식이 이 저장소의 철학을 꽤 잘 보여준다.

## 설치 흐름은 생각보다 단순하다

설치만 놓고 보면 구조는 의외로 단순하다.

### 1단계: Hermes를 먼저 설치한다

Oh My Hermes는 Hermes가 먼저 있어야 작동한다. `install.sh`도 `~/.hermes` 폴더가 없으면 바로 멈춘다.

즉 순서는 무조건 이렇다.

1. Hermes Agent 설치
2. Hermes 초기 실행
3. 그다음 Oh My Hermes 설치

초보자라면 여기서 가장 많이 막힐 가능성이 높다. Oh My Hermes를 먼저 설치하려 하면 실패한다.

### 2단계: install.sh가 파일을 복사한다

이 저장소의 `install.sh`는 프로그램을 빌드하지 않는다. 그냥 필요한 파일을 적절한 위치로 복사한다.

- skills → `~/.hermes/skills/`
- workflows → `~/.hermes/workflows/`
- agents → `~/.hermes/agents/`

이 점이 중요하다. 즉 “설치”라고 해도 복잡한 바이너리 설치가 아니라 <strong>Hermes가 읽을 파일을 넣는 과정</strong>이다.

### 3단계: verify.sh로 확인한다

`verify.sh`는 꽤 마음에 드는 스크립트였다. 초보자가 설치 뒤에 꼭 확인해야 할 지점을 체크해 준다.

- `hermes` 명령이 있는지
- `~/.hermes/skills/` 가 있는지
- 핵심 스킬 파일이 들어갔는지
- 에이전트 파일이 들어갔는지
- 워크플로우 파일이 들어갔는지

초보자라면 설치보다 이 확인 단계가 더 중요하다. 실제로 이런 류 도구는 “설치된 줄 알았는데 반만 들어간 상태”가 흔하기 때문이다.

## 이 프로젝트의 핵심은 choose-engine 사고방식이다

개인적으로 가장 잘 만든 문서 중 하나는 `docs/engines.md` 와 `skills/choose-engine.md` 였다.

여기서는 “무슨 모델이 더 좋냐”보다 “이 일을 누가 맡아야 하냐”를 먼저 묻는다.

판단 기준은 대략 이렇다.

- 운영 작업이면 Hermes가 직접 처리
- 복잡한 다중 파일 작업이면 Claude Code
- 빠른 단일 파일 수정이면 Codex
- UI/UX 탐색은 Claude Design 같은 인간 개입 단계

이게 왜 좋냐면, 초보자가 가장 자주 하는 실수가 모든 일을 하나의 AI에게 한 번에 맡기는 것이기 때문이다. 이 저장소는 그걸 막아준다.

## 초보 개발자에게 특히 좋은 부분

### 1) 요구사항을 먼저 정리하게 만든다

`clarify-requirements` 와 `product-brief` 흐름은, 코딩부터 들어가려는 습관을 한 번 멈추게 한다.

이건 초보자에게 특히 중요하다. 대부분은 구현이 어려운 게 아니라, 무엇을 만들지 애매한 상태에서 시작해서 중간에 무너진다.

### 2) 배포와 헬스체크를 개발 흐름 안에 넣어둔다

초보 개발자들은 코드 작성까지만 작업이라고 생각하는 경우가 많다. 그런데 이 저장소는 배포와 헬스체크를 기본 흐름 안에 넣어둔다.

즉,

- 만들고 끝이 아니라
- 배포하고
- URL을 받고
- `/api/health`를 확인하고
- 알림까지 보내는 것

까지를 한 세트로 본다.

이 관점은 꽤 건강하다.

### 3) “24시간 돌아가는 운영자”라는 그림이 선명하다

README의 가장 강한 메시지는 이것이다.

당신이 터미널을 열지 않아도, Hermes가 VPS나 로컬 머신에서 계속 돌아가며

- GitHub를 보고
- 이슈를 고르고
- PR을 만들고
- QA를 하고
- 승인을 물어보고
- 배포 후 상태를 확인한다

는 그림이다.

이걸 지나치게 과장해서 받아들이면 위험하지만, 반대로 <strong>Hermes를 단발성 채팅 도구가 아니라 장기 운영 프로세스로 본다</strong>는 점은 매우 인상적이었다.

## 읽으면서 바로 보인 주의점도 있다

이 프로젝트를 칭찬만 하고 끝내면 오히려 초보자에게 불친절하다. 실제로 읽다 보면 몇 가지 주의점이 있다.

### 1) Hermes를 모르면 오히려 더 헷갈릴 수 있다

이 프로젝트는 Hermes의 장점을 이미 어느 정도 이해하고 있다는 전제를 깔고 있다.

그래서 초보자가 처음부터 Oh My Hermes README만 읽으면,

- Hermes는 또 뭐지?
- 왜 VPS가 필요하지?
- Claude Code와 Codex는 왜 또 따로 있지?
- 왜 Slack과 Telegram이 나오지?

같은 질문이 한꺼번에 몰릴 수 있다.

그래서 진짜 초보자라면 권장 순서는 이렇다.

1. Hermes 기본 개념 이해
2. Hermes 설치와 단일 명령 사용 경험
3. 그 다음 Oh My Hermes 읽기

### 2) 문서 숫자가 조금 흔들린다

읽다 보면 숫자가 약간 엇갈리는 부분이 있다.

- README는 20 skills 라고 말한다
- 웹 요약 일부와 installation 문구에는 18 skills 라고 적혀 있다
- 실제 `verify.sh`는 20개 스킬을 체크한다

큰 문제는 아니지만, 초보자라면 “설치가 덜 된 건가?” 하고 불안할 수 있다. 이런 부분은 나중에 문서 정리가 한 번 더 필요해 보였다.

### 3) Claude Design은 자동화가 아니다

이 저장소는 이 점을 꽤 정직하게 말한다. Claude Design은 인간이 직접 해야 하는 단계라고 선을 긋는다.

이건 오히려 장점이다. 자동화할 수 없는 걸 되는 척하지 않기 때문이다.

### 4) 실제 운영엔 외부 계정과 CLI가 꽤 필요하다

초보자 입장에서는 이 부분도 중요하다.

정말 다 쓰려면 결국 필요해지는 게 많다.

- GitHub 계정과 토큰
- Vercel 계정과 CLI
- Supabase 계정과 CLI
- Slack webhook
- 항상 켜둘 VPS 또는 머신

즉, “설치만 하면 끝”인 프로젝트는 아니다. 제대로 굴리려면 운영 준비물이 꽤 있다.

## 그럼 누가 써보면 좋을까

### 잘 맞는 사람

- Hermes를 이미 설치해서 조금 써본 사람
- AI 에이전트를 실제 프로젝트 운영 흐름에 붙여보고 싶은 사람
- GitHub, Vercel, Supabase를 묶은 기본 SaaS 흐름을 빠르게 만들고 싶은 사람
- AI를 혼자 코딩시키는 데서 끝내지 않고 역할 분담 구조로 운영해보고 싶은 사람

### 아직 이른 사람

- Git, GitHub, 배포 개념이 아직 거의 없는 완전 초보
- Hermes 자체를 아직 한 번도 안 써본 사람
- 일단 간단한 챗봇처럼만 AI 도구를 쓰고 싶은 사람

이 경우엔 먼저 Hermes나 GitHub Pages 같은 더 작은 흐름부터 익힌 뒤 들어오는 게 좋다.

## 초보 개발자에게 추천하는 읽기 순서

이 저장소를 처음 볼 때는 아래 순서가 가장 덜 힘들다.

1. `README.md`
2. `docs/installation.md`
3. `docs/architecture.md`
4. `docs/workflows.md`
5. `docs/engines.md`
6. 마지막에 `cto-loop.md`

처음부터 CTO loop 문서로 들어가면 멋있어 보이긴 하는데, 구조가 머리에 안 잡힌다. 먼저 설치와 구조를 보고, 그다음 큰 그림으로 올라가는 게 훨씬 낫다.

## 실제로 한 것

1. 저장소의 README와 설치, 아키텍처, 워크플로우, 엔진 라우팅 문서를 직접 읽었다.
2. `install.sh` 와 `verify.sh` 를 확인해 실제 설치가 무엇을 하는지 추적했다.
3. 초보 개발자가 가장 헷갈릴 지점을 기준으로 개념, 설치 구조, 장점, 주의점을 다시 묶어 정리했다.

## 막혔던 지점

> 문서는 잘 써놨지만, 처음 보는 사람 기준으로는 레이어가 많아 한 번에 이해하기 어렵다.

Hermes, Claude Code, Codex, Claude Design, Vercel, Supabase, Slack, cron, kanban이 한 문서 안에서 빠르게 이어지다 보니, 익숙한 사람에게는 좋지만 초보자에겐 숨이 찰 수 있다. 그래서 이번 글에서는 기능 나열보다 “이 프로젝트는 정확히 무엇이고, 무엇은 아니며, 어디부터 보면 좋은가”를 먼저 세우는 쪽으로 정리했다.

  <li>완전 초보라면 Hermes와 GitHub/Vercel 기본기부터 먼저 익히는 편이 낫다.</li>
</ul>

## 남겨둘 판단

Oh My Hermes는 “AI가 다 해준다”는 식의 가벼운 데모 프로젝트가 아니다. 오히려 그 반대다. AI 에이전트를 실제 소프트웨어 운영 흐름에 붙이려면 어떤 기본 습관과 역할 분담이 필요한지를 꽤 성실하게 문서화한 저장소에 가깝다.

그래서 이 프로젝트의 진짜 매력은 화려한 자동화보다도, <strong>운영의 빈칸을 메우는 태도</strong>에 있다.

초보 개발자라면 이 저장소를 그대로 전부 따라 하기보다,

- 에이전트를 한 명이 아니라 역할로 나눈다는 생각
- 배포와 헬스체크를 개발의 마지막이 아니라 기본으로 넣는 습관
- 설치보다 확인이 중요하다는 감각

이 세 가지만 먼저 가져가도 충분히 값어치가 있다.
