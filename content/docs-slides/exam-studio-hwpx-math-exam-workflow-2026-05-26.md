# PDF에서 HWPX 수학 시험지까지 한 번에 가려는 시도, `exam-studio`를 읽어봤다

시험지 작업을 해본 사람은 안다. PDF에서 문제를 뽑고, 그림을 다듬고, 해설을 붙이고, 마지막엔 한글 문서 양식에 맞춰 다시 손보는 과정이 생각보다 훨씬 오래 걸린다. 특히 수학 시험지는 수식, 도형, 보기 배치, 점수 표기, 머리말 양식까지 한 번에 맞아야 해서 자동화가 더 까다롭다.

그런데 이번에 본 `exam-studio`는 이 지점을 꽤 정면으로 건드린다. 단순히 “PDF를 읽는 AI 툴”이 아니라, **수학 기출 PDF를 읽고 HWPX 시험지로 조립하는 작업실**에 가깝다. 웹 UI는 Next.js로 만들고, 실제 문서 조립은 Python으로 처리하고, 그 사이에 Claude·Gemini 계열 AI를 넣어 문제 추출·해설·그림 처리까지 묶어두었다.

## 먼저 출처부터 밝히자

이 글에서 다루는 프로젝트의 직접 출처는 아래 GitHub 저장소다.

- 저장소: `PNKmath/exam-studio`
- URL: <https://github.com/PNKmath/exam-studio>
- 저장소 설명: **“Exam Studio — HWPX 수학 기출 시험지 제작 스튜디오 (Next.js + Python). NGD Studio 기반 de-branded 배포본.”**

즉 이 저장소는 스스로를 **NGD Studio 기반 de-branded 배포본**이라고 소개하고 있다. 또 내가 확인한 기준으로는 저장소 루트에 별도 `LICENSE` 파일은 보이지 않았다. 그래서 실사용이나 재배포를 고민한다면, 기능만 보기 전에 **원저작 맥락과 사용 조건을 먼저 확인하는 태도**가 맞다.

## 먼저 결론

- `exam-studio`는 단순 요약 도구가 아니라, **PDF → 추출 → 해설 → 그림 처리 → HWPX 조립**까지 이어지는 시험지 제작 파이프라인을 겨냥한 프로젝트다.
- 구조는 꽤 인상적이다. **Next.js 웹 UI + Python HWPX 엔진 + AI 단계별 오케스트레이션**이 분리되어 있어서, 무엇이 화면이고 무엇이 문서 빌더인지 비교적 명확하다.
- 특히 흥미로운 지점은 HWPX를 “한글에서 수동 저장”으로 다루지 않고, **ZIP+XML 문서 구조를 직접 조작하는 빌드 대상**으로 본다는 점이다.
- 다만 이런 프로젝트는 곧바로 “누구나 바로 쓰기 좋은 도구”라고 보긴 어렵다. **AI CLI 의존성, HWPX 양식 매핑, 그림 처리 품질, 라이선스/출처 확인** 같은 현실 조건도 같이 봐야 한다.
- 교육 현장이나 문서 자동화 관점에서는 꽤 흥미롭지만, 핵심 가치는 마법 같은 완전 자동화보다 **시험지 제작의 병목을 어디까지 구조화했는가**에 있다.

## 이 프로젝트가 실제로 하려는 일

README 설명을 한 줄로 줄이면 이렇다.

> 수학 기출 PDF를 읽고, 문제와 해설과 그림을 처리한 뒤, 최종 결과를 HWPX 시험지 문서로 조립하는 워크플로우 도구.

즉 이 프로젝트는 그냥 문제를 OCR 하는 데서 멈추지 않는다.

- PDF에서 문제를 추출하고
- 필요한 해설을 생성·검증하고
- 그림을 잘라내고 다시 다듬고
- 마지막엔 한컴 문서 포맷(HWPX)에 맞춰 시험지 형태로 조립한다.

이 흐름은 특히 한국 교육 문서 환경을 잘 이해하고 있어야 떠올릴 수 있는 구조다. “PDF를 읽는다”보다 “결국 HWPX로 끝나야 한다”가 더 중요하다는 점을 전제로 깔고 있기 때문이다.

## 구조를 보면 더 또렷해진다

이 저장소의 큰 구조는 대략 세 층이다.

### 1) 웹 UI: `studio/`의 Next.js 프론트엔드
사용자는 브라우저에서 시험지 제작, 히스토리, 설정 화면을 다룬다. 포트도 명시되어 있고, SSE 로그 서버를 따로 둔 걸 보면 **단순 업로드 페이지보다 작업 진행 상황을 보여주는 제작 스튜디오** 쪽에 더 가깝다.

### 2) Python 문서 엔진
루트에 있는 `build_hwpx.py`, `assemble.py`, `tables.py`, `figure_processor.py` 같은 파일이 실제 조립 엔진 역할을 맡는다. 여기서 핵심은 HWPX를 한 번 더 저장하는 게 아니라, **ZIP으로 열고 XML을 직접 바꿔 다시 조립한다**는 점이다.

### 3) AI 파이프라인
README와 아키텍처 문서를 보면 Claude / Gemini 계열을 추출·해설·그림 처리에 배치한다. 또 `Codex CLI`나 `Claude Code CLI`를 실행 레이어로 붙이는 흐름도 이미 포함돼 있다.

이 세 층이 나뉘어 있다는 건 꽤 중요하다. 화면, 문서 생성, AI 호출이 한 덩어리로 섞여 있지 않아서, 어디가 문제인지 추적하기가 그나마 쉽다.

## 아키텍처 문서에서 특히 눈에 띈 부분

`docs/architecture.md`를 읽으면, 이 프로젝트는 최소한 개념상으로 아래 파이프라인을 갖고 있다.

1. `reader` 단계: PDF를 이미지로 변환하고 문제·수식·해설을 추출
2. `figure` 단계: 그림 영역을 crop 하고 재생성/정리
3. `builder` 단계: JSON과 이미지를 HWPX로 조립

이게 중요한 이유는 단순하다.

시험지 자동화에서 제일 힘든 건 “한 번에 다 잘하는 모델”을 찾는 게 아니라,
- 읽는 단계
- 그림 다루는 단계
- 문서 양식에 넣는 단계

의 실패 지점을 분리하는 일이기 때문이다.

이 저장소는 적어도 설계 문서 수준에서는 그 분리를 꽤 의식하고 있다.

## HWPX를 다루는 방식이 이 프로젝트의 진짜 핵심이다

이 레포를 그냥 AI 프로젝트로만 보면 반만 읽은 셈이다. 진짜 흥미로운 부분은 **HWPX를 어떻게 다루는가**에 있다.

문서 설명을 보면 HWPX를 다음처럼 보고 있다.

- ZIP 패키지
- 내부 XML 문서 묶음
- `section0.xml`, `header.xml`, `masterpage0.xml`, `content.hpf`, `BinData` 등을 직접 갱신

즉 HWPX를 “한글 프로그램 파일”이 아니라, **템플릿 기반 문서 빌드 시스템**으로 읽고 있다. 이건 아주 한국적인 문제를 꽤 엔지니어링스럽게 푼 접근이다.

특히 시험지 같은 문서는
- 수식 크기
- 표 위치
- 이미지 삽입
- 머릿말 텍스트
- 문제 번호와 점수 배치

가 다 얽혀 있어서, 그냥 텍스트 생성보다 훨씬 까다롭다. 이 저장소는 그 어려움을 피하지 않고, 오히려 XML 레벨로 내려가서 다루려 한다.

## 설치 경험까지도 “교사/실무자용”으로 맞추려 한 흔적이 보인다

README에서 또 하나 눈에 띄는 건 설치 안내다.

- macOS / Linux는 `bootstrap.sh`
- Windows는 `bootstrap.ps1`
- 설치 후엔 더블클릭 런처 제공
- Node 22+ 자동 설치 보조
- Python 3.10+만 미리 요구
- Codex CLI 또는 Claude Code CLI 로그인 흐름까지 포함

이건 전형적인 개발자용 레포 README와 조금 다르다. 단순히 `pnpm install`만 적어둔 게 아니라, **비개발자 혹은 반개발자 사용자도 실제로 켜볼 수 있게 만들려는 의도**가 보인다.

이 점은 분명 장점이다. 교육 현장 도구는 기능만 좋아도 소용없고, 결국 “누가 실제로 켜서 쓸 수 있느냐”가 중요하기 때문이다.

## 이 프로젝트가 특히 흥미로운 이유

내가 보기엔 이 프로젝트의 가치는 “AI로 시험지 만들기”라는 문장보다 아래 네 가지에 있다.

### 1) PDF를 최종 결과물이 아닌 중간 재료로 본다
많은 도구는 PDF 읽기에서 끝난다. 이건 다르다. PDF는 시작점일 뿐이고, 목표는 HWPX 결과물이다.

### 2) 한국 문서 현실을 정면으로 다룬다
한글(HWPX) 양식, 수학 수식, 시험지 머릿말, 보기 배치 같은 문제는 글로벌 SaaS가 대충 해결해주지 않는다. 이 프로젝트는 그 지역적 현실을 정면으로 본다.

### 3) AI 호출을 단계별로 나눠 둔다
추출, 해설, 그림 처리를 나눠 보면 어느 부분이 흔들리는지 알 수 있다. 이건 실제 운영에서 중요하다.

### 4) 결과물을 “편집 가능한 문서”로 돌려준다
최종 산출물이 PDF가 아니라 HWPX라는 건, 결국 사람이 마지막 손질을 할 수 있는 상태로 준다는 뜻이다. 교육 현장에서는 이게 꽤 큰 차이다.

## 동시에 같이 봐야 할 한계도 있다

좋은 점만 보면 오히려 판단이 흐려진다. 이 프로젝트는 분명 매력적이지만, 같이 봐야 할 현실도 있다.

### 1) 출처와 라이선스 확인이 먼저다
저장소 설명에 NGD Studio 기반 de-branded 배포본이라고 적혀 있고, 내가 본 기준으로는 별도 라이선스 파일도 없었다. 그래서 기능 분석과 별개로, **어디서 왔는지와 어떤 조건으로 써도 되는지**를 먼저 확인해야 한다.

### 2) HWPX 양식 매핑은 생각보다 까다롭다
아키텍처 문서에도 `charPrIDRef` 매핑 문제 같은 미해결 과제가 남아 있다. 이 말은 곧, 문서 양식을 바꾸거나 다른 학교 양식을 넣으면 예상보다 쉽게 깨질 수 있다는 뜻이기도 하다.

### 3) AI 품질보다 후처리 품질이 더 중요할 수 있다
시험지는 내용만 맞다고 끝이 아니다. 수식 표시, 그림 잘림, 점수 위치, 줄바꿈, 머릿말 spacing 같은 문서 품질이 신뢰를 좌우한다.

### 4) “완전 자동화”보다 “반자동 작업실”로 보는 편이 정확하다
이 도구를 한 번에 완성형 시험지 자동 생성기라고 기대하면 실망할 수 있다. 오히려 **사람이 마지막에 검수·수정할 수 있는 반자동 제작 스튜디오**로 보는 편이 맞다.

## 이런 사람에게 특히 흥미롭다

- 수학 시험지나 학습지를 자주 만드는 교사
- HWPX 자동화에 관심 있는 개발자
- 한국형 문서 워크플로우 자동화를 고민하는 사람
- PDF → 구조화 데이터 → 편집 가능 문서 변환 파이프라인을 보고 싶은 사람
- Claude Code / Codex / Gemini를 실제 문서 제작 흐름에 넣어보고 싶은 사람

## 실제로 한 것

1. GitHub 저장소 `PNKmath/exam-studio`의 README, 아키텍처 문서, 패키지 구성을 직접 읽었다.
2. 출처를 먼저 확인하기 위해 저장소 설명과 원문 구조를 보고, **NGD Studio 기반 de-branded 배포본**이라는 자기 설명을 앞에 세웠다.
3. 기능 목록보다 **PDF → AI 처리 → HWPX 조립**이라는 전체 흐름이 어떻게 짜여 있는지 중심으로 다시 정리했다.
4. 단순 칭찬 글이 되지 않도록, 라이선스 부재·양식 매핑 난도·후처리 품질 같은 현실 조건도 같이 넣었다.

## 막혔던 지점

README와 저장소 설명만 봐도 기능은 꽤 분명하다. 하지만 사용자가 이번에 특히 “출처를 밝히고”라고 요청했기 때문에, 이 글은 도구 소개보다 먼저 **누가 공개했고, 스스로 어떤 기반이라고 밝히는지, 라이선스는 보이는지**를 확인하는 쪽이 더 중요했다.

## 남겨둘 판단

`exam-studio`의 진짜 가치는 “시험지를 AI로 만들어준다”는 문구보다, **한국형 시험지 제작의 지저분한 현실을 파이프라인으로 분해해 보려는 시도**에 있다.

PDF를 읽고, 수식과 그림을 건드리고, 해설을 붙이고, 마지막엔 HWPX라는 실제 현장 문서 포맷으로 조립하는 흐름은 결코 쉬운 문제가 아니다. 그래서 이 프로젝트는 완벽한 자동화 성공담이라기보다, **문서 자동화가 어디서부터 진짜 어려워지는지 보여주는 꽤 좋은 사례**로 읽는 편이 더 정확하다.
